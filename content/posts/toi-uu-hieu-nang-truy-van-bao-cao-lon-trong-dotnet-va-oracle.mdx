## 1. Bức tranh bài toán: Tại sao báo cáo chạy nhanh ở UAT nhưng treo cứng ở Production?

Trong các hệ thống quản trị doanh nghiệp sử dụng **.NET** kết hợp **Oracle Database**, chức năng tra cứu và kết xuất báo cáo đối soát kỳ (qua **RDLC Report** hoặc luồng xuất tệp phân tích) thường hoạt động rất mượt ở giai đoạn đầu khi bảng giao dịch chỉ có vài chục nghìn dòng. Tuy nhiên, khi bảng `LEDGER_TRANSACTIONS` vượt mốc **18 triệu bản ghi** (mỗi kỳ báo cáo lọc khoảng `2 triệu dòng` đủ điều kiện), API tra cứu phân trang và kết xuất báo cáo bắt đầu vọt lên `48 giây`, tiêu tốn gần `1.8 GB RAM` cho mỗi lượt chạy đồng thời.

Khi đi sâu vào cả hai tầng — **Oracle Cost-Based Optimizer (CBO)** và **cơ chế cấp phát bộ nhớ của .NET CLR** — chúng tôi xác định chi phí 48 giây này không nằm ở tốc độ đĩa cứng mà xuất phát từ **3 bẫy hiệu năng ngầm**:
1. Chuyển đổi kiểu dữ liệu ngầm định (`SYS_OP_C2C`) vô hiệu hóa hoàn toàn chỉ mục.
2. Phân trang kiểu `OFFSET ... FETCH` buộc Oracle quét và vứt bỏ hàng triệu dòng ở các trang sâu.
3. Nạp toàn bộ danh sách thực thể vào bộ nhớ bằng `ToListAsync()` gây phân mảnh **Large Object Heap (LOH)** trước khi đưa vào bộ kết xuất RDLC.

## 2. Đọc vị DBMS_XPLAN: Phát hiện sát thủ thầm lặng SYS_OP_C2C

Đầu tiên, chúng tôi thu thập kế hoạch thực thi thực tế (`A-Rows` so với `E-Rows`) của câu truy vấn gốc ngay sau khi chạy bằng gói `DBMS_XPLAN.DISPLAY_CURSOR`:

```sql title="inspect-actual-plan.sql"
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(
        sql_id          => '7g9k2m1x8p4q1',
        cursor_child_no => 0,
        format          => 'ALLSTATS LAST +PEEKED_BINDS +PREDICATE'
    )
);
```

Kết quả trả về trong phần `Predicate Information` chỉ ra ngay nguyên nhân khiến Oracle chọn `TABLE ACCESS FULL` đọc hơn `240,000 buffers` dù cột `MERCHANT_CODE` và `CREATED_AT` đã được đánh Index đơn lẻ:

```text title="xplan-before-optimization.txt"
-----------------------------------------------------------------------------------------------------------
| Id  | Operation          | Name                | Starts | E-Rows | A-Rows |   A-Time   | Buffers | Reads |
-----------------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT   |                     |      1 |        |    500 |00:00:39.42 |     248K|   192K|
|   1 |  SORT ORDER BY     |                     |      1 |    500 |    500 |00:00:39.42 |     248K|   192K|
|*  2 |   TABLE ACCESS FULL| LEDGER_TRANSACTIONS |      1 |  1840K |  2015K |00:00:34.18 |     248K|   192K|
-----------------------------------------------------------------------------------------------------------

Predicate Information (identified by operation id):
---------------------------------------------------
   2 - filter((SYS_OP_C2C("MERCHANT_CODE")=:P_MERCHANT
              AND TRUNC("CREATED_AT")>=:P_FROM_DATE
              AND "STATUS"='SETTLED'))
```

<Callout type="investigation" title="Giải mã hai lỗi mất tính SARGable trong Predicate #2">
  1. **`SYS_OP_C2C("MERCHANT_CODE")=:P_MERCHANT`**: Cột `MERCHANT_CODE` dưới Oracle có kiểu `VARCHAR2(32)`, nhưng tham số chuỗi mặc định từ EF Core / C# được truyền xuống dưới dạng `NVARCHAR2` (`OracleDbType.NVarchar2`). Do độ ưu tiên kiểu dữ liệu, Oracle buộc phải ép hàm `SYS_OP_C2C` lên từng dòng của bảng, làm cây B-Tree Index trên `MERCHANT_CODE` trở nên vô dụng.
  2. **`TRUNC("CREATED_AT")>=:P_FROM_DATE`**: Bọc hàm `TRUNC()` quanh cột ngày tháng tiếp tục ngăn cản Optimizer thực hiện phép quét khoảng (`INDEX RANGE SCAN`).
</Callout>

## 3. Thiết kế Covering Composite Index & Keyset Pagination

### 3.1. Khôi phục SARGability và loại bỏ Table Lookup

Chúng tôi viết lại điều kiện lọc theo khoảng nửa mở `[fromDate, toDateExclusive)`, định kiểu tường minh `VARCHAR2(32)` ở tầng `.NET`, đồng thời thiết kế một **Covering Composite Index** tuân theo quy tắc **Equality Columns -> Sort/Range Columns -> Included Payload Columns**:

```sql title="create-covering-index.sql"
CREATE INDEX idx_ledger_rpt_covering ON ledger_transactions (
    merchant_code,
    status,
    created_at DESC,
    txn_id DESC
)
COMPRESS 2
TABLESPACE tbs_idx_app;
```

```diff title="query-sargable-refactor.diff"
 SELECT txn_id, merchant_code, created_at, net_amount, currency_code, reference_no
 FROM ledger_transactions
-WHERE merchant_code = :p_merchant_nvarchar
-  AND TRUNC(created_at) BETWEEN :p_from_date AND :p_to_date
+WHERE merchant_code = :p_merchant_varchar2
+  AND status = 'SETTLED'
+  AND created_at >= :p_from_date
+  AND created_at <  :p_to_date_next_day
+  AND (:p_cursor_date IS NULL
+       OR (created_at < :p_cursor_date)
+       OR (created_at = :p_cursor_date AND txn_id < :p_cursor_id))
 ORDER BY created_at DESC, txn_id DESC
-OFFSET 500000 ROWS FETCH NEXT 500 ROWS ONLY;
+FETCH FIRST 500 ROWS ONLY;
```

Kế hoạch thực thi mới (`xplan-after`) giảm lượng đọc bộ đệm từ `248,000 Buffers` xuống chỉ còn **`11 Buffers`** và hoàn toàn không phát sinh bước `SORT ORDER BY` nhờ thứ tự khóa của Index khớp 100% với mệnh đề `ORDER BY`:

```text title="xplan-after-optimization.txt"

| Id  | Operation                     | Name                    | Starts | E-Rows | A-Rows |   A-Time   | Buffers |
----------------------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT              |                         |      1 |        |    500 |00:00:00.01 |      11 |
|*  1 |  COUNT STOPKEY                |                         |      1 |        |    500 |00:00:00.01 |      11 |
|   2 |   TABLE ACCESS BY INDEX ROWID | LEDGER_TRANSACTIONS     |      1 |    500 |    500 |00:00:00.01 |      11 |
```

### 3.2. Bảng đánh đổi giữa các chiến lược xử lý báo cáo lớn

| Chiến lược kỹ thuật | Độ trễ ở trang thứ 1,000 | Mức tiêu thụ RAM | Phù hợp với nghiệp vụ |
| :--- | :--- | :--- | :--- |
| `OFFSET / FETCH` truyền thống | `18.5 s` (tăng tuyến tính) | Thấp ở App, rất nặng CPU DB | Bảng nhỏ dưới `50,000` dòng |
| **Keyset (Seek) Pagination** | **`8 ms` (hằng số `O(log N)`)** | **Cực thấp (`< 5 MB`)** | Tra cứu lịch sử giao dịch, cuộn vô tận, xuất lô tuần tự |
| Materialized View tổng hợp trước | `4 ms` | Tốn thêm dung lượng lưu trữ | Dashboard thống kê tổng hợp theo ngày/tháng |

<Callout type="warning" title="Đánh đổi khi dùng Keyset Pagination">
  Keyset Pagination không hỗ trợ nhảy trực tiếp tới một số trang bất kỳ (ví dụ bấm thẳng từ trang 1 sang trang 472) mà điều hướng qua con trỏ `(lastCreatedAt, lastTxnId)`. Với giao diện tra cứu giao dịch tài chính/kho vận, kết hợp bộ lọc khung giờ cụ thể cùng nút *"Trang tiếp theo"* mang lại trải nghiệm ổn định vượt trội.
</Callout>

## 4. Tối ưu luồng đọc Streaming trên .NET 8 cho RDLC & Xuất báo cáo

Với tác vụ kết xuất trọn bộ báo cáo tổng hợp gồm hàng trăm nghìn đến 2 triệu bản ghi, sai lầm phổ biến nhất ở tầng `.NET` là nạp toàn bộ kết quả EF Core bằng `ToListAsync()` (tạo mảng đối tượng khổng lồ nằm thẳng trên **Large Object Heap >= 85,000 bytes**).

Giải pháp chuẩn là đẩy phép nhóm tổng hợp (Subtotals theo ngày/loại giao dịch) xuống SQL cho phần biểu đồ/bảng tóm tắt RDLC, còn luồng chi tiết sử dụng `IAsyncEnumerable<T>` kết hợp `OracleDataReader` cấu hình `FetchSize` hợp lý để ghi trực tiếp ra `Stream`:

```csharp title="LedgerReportStreamService.cs" {12-13,22-25}
public async IAsyncEnumerable<LedgerReportRow> StreamSettlementRowsAsync(
    string merchantCode,
    DateTime fromUtc,
    DateTime toExclusiveUtc,
    [EnumeratorCancellation] CancellationToken ct)
{
    await using var connection = new OracleConnection(_readOnlyConnectionString);
    await connection.OpenAsync(ct);

    await using var command = connection.CreateCommand();
    command.BindByName = true;
    // Đọc theo lô mạng 2MB mỗi lần round-trip thay vì mặc định 128KB của ODP.NET
    command.FetchSize = 2 * 1024 * 1024;
    command.CommandText = ReportSqlQueries.SelectSargableLedgerRows;

    // Khai báo tường minh OracleDbType.Varchar2 để chặn đứng hàm ép kiểu ngầm SYS_OP_C2C
    command.Parameters.Add("p_merchant_varchar2", OracleDbType.Varchar2, 32).Value = merchantCode;
    command.Parameters.Add("p_from_date", OracleDbType.TimeStamp).Value = fromUtc;
    command.Parameters.Add("p_to_date_next_day", OracleDbType.TimeStamp).Value = toExclusiveUtc;

    await using var reader = await command.ExecuteReaderAsync(
        CommandBehavior.SequentialAccess,
        ct);

    while (await reader.ReadAsync(ct))
    {
        yield return new LedgerReportRow(
            TxnId: reader.GetInt64(0),
            MerchantCode: reader.GetString(1),
            CreatedAt: reader.GetDateTime(2),
            NetAmount: reader.GetDecimal(3),
            Currency: reader.GetString(4));
    }
}
```

<Callout type="solution" title="Hiệu quả kết hợp FetchSize + SequentialAccess">
  Thiết lập `FetchSize = 2MB` giảm số vòng lặp mạng giữa container `.NET 8` và máy chủ `Oracle 19c` hơn **16 lần** khi đọc luồng lớn, trong khi `CommandBehavior.SequentialAccess` kết hợp `yield return` giữ mức cấp phát bộ nhớ của tiến trình ổn định dưới `65 MB` bất kể số dòng xuất ra là 100 nghìn hay 2 triệu dòng.
</Callout>
